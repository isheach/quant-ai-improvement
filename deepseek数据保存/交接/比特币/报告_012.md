## 3. ★★推断（高置信）：这不是"组合丢失"，而是 **MT5 遗传算法（GA）** 的正常行为

### 3.1 决定性证据：`Pass` 编号的取值分布
我按 Pass 排序后看前 25 个：
```
Pass  0: Donchian=30  EMA=50   Slope=9   ClosePos=0.75
Pass  1: Donchian=48  EMA=50   Slope=13  ClosePos=0.75
Pass  2: Donchian=30  EMA=50   Slope=7   ClosePos=0.70
Pass  3: Donchian=66  EMA=50   Slope=5   ClosePos=0.55
Pass  4: Donchian=30  EMA=100  Slope=11  ClosePos=0.65
...
```
**而最后 10 个 Pass（147~156）：**
```
Pass=147 Donchian=12  EMA=150  Slope=13  0.55
Pass=148 Donchian=66  EMA=125  Slope=9   0.75
Pass=149 Donchian=12  EMA=150  Slope=9   0.50
Pass=150 Donchian=12  EMA=50   Slope=3   0.75
Pass=151 Donchian=12  EMA=50   Slope=11  0.75
Pass=152 Donchian=12  EMA=50   Slope=9   0.75
Pass=153 Donchian=12  EMA=125  Slope=13  0.60
Pass=154 Donchian=12  EMA=175  Slope=7   0.55
Pass=155 Donchian=12  EMA=50   Slope=5   0.55
Pass=156 Donchian=12  EMA=75   Slope=5   0.75
```
→ **后段参数高度聚集在 `Donchian=12` 附近** —— 这是**种群收敛（population convergence）** 的典型特征，**不是笛卡尔积穷举**。
→ 穷举会均匀覆盖全空间（前 25 个确实像随机初始化），**但不会出现"后段全部聚到同一档"**。

### 3.2 与 `Optimization=2` 一致
我读了 `opt_OPT_btcgrid-001.ini`：
```
[Tester]
Expert=dshtrend\opt_btcgrid-001
Symbol=BTCUSDm
Period=M1
Model=2
Optimization=2        ← ★
FromDate=2018.02.09
ToDate=2024.05.31
Report=rep_OPT_btcgrid-001
```
**MT5 里 `Optimization=1` = 慢速完整算法（穷举）、`Optimization=2` = 快速遗传算法。**（此点我**无法用官方文档二次确认**——本会话的 web 检索工具不可用——所以标为**推断**，但它与 3.1 的收敛证据、以及"实际组数 << 声明组数"完全自洽。）

### 3.3 由此解释三件此前无法解释的现象
1. **为什么组数不足**：GA 不遍历全部组合，只按种群+代数迭代 → 组数天然远小于笛卡尔积，且随收敛情况波动（157/166/148/150/133/133）。
2. **为什么 005 与 006 都是 133 组但耗时差 14.7 倍**：GA 的**代数**相近，但每组回测的**窗口长度**不同（训练段 vs 压力窗口）→ 组数相同、耗时不同。**这排除了"固定组数上限"和"时间上限"两种解释**，而 GA 是唯一自洽的解释。
3. **为什么 `0 profitable`**：GA 是**随机+贪心**的，**不保证采到我的已知盈利点**。而 `btc-138` 的窗口/参数在本网格里**根本没被采到**（我按 `Donchian=48/EMA=200/Slope=10/ClosePos=0.65` 去 157 行里查过 —— **不在其中**）。**GA 从没有一个正收益个体可供进化，于是全程在坏区域里打转。**

## 4. ★★事实（第二个独立问题）：网格的基础配置**本身是坏的**

我从 `opt_btcgrid-001.set` 读到：
```
InpAllowShort=true||false||0||true||N      ← ★ 固定为 true
InpUseDDKill=false||false||0||true||N
InpLatencyTicks=1||1||1||10||N
InpLatencyMs=0||300||1||3000||N
InpFilterRequireSlope=true
InpUseEntryQuality=true
```
**`InpAllowShort=true` 是 `btcswing` 基线的默认值**，而**我全部三段为正的配置（btc-137/138/139）都显式写了 `InpAllowShort=false`**。

**对照（同一参数族、同一训练窗口）**：

| 配置 | AllowShort | 笔数 | DD% | 净利 |
|---|---|---:|---:|---:|
| btc-138（单跑） | **false** | 344 | 50.21 | **+412.52** |
| btcgrid-001 中位（157 组） | **true** | **9,845** | **100.00** | **−297** |

→ **同一参数族，只因 `AllowShort` 与"GA 采样点"不同，结果从 +412.52 变成全灭。**
→ **即使 GA 换成穷举，只要 `AllowShort=true`，这个网格也大概率产出大量爆仓个体**（因为网格的 `InpSL_ATR` 起点 1.0、`InpTrail_ATR` 起点 2.0 会扫到更紧的出场地带，配合双向 churn 极易磨穿账户）。

**这是我网格设计的一个失误**：我把 `InpAllowShort=true` 直接从 `btcswing` 基线带进网格，而没有意识到**它是我在报告_008 里亲手定位为"验证段唯一亏损来源"的那个开关**。**我为此负责。**
