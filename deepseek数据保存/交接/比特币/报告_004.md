## 1. 事实：`risk_money` 语义已被源码确证（总调度提供行号 + **我已亲自逐行复核**）

总调度给出的写入链，**我按项目纪律自己重读了每一行**（`dsh_TrendCore.mq5`），结果**全部核对一致**：

| 行号 | 我重读到的实际内容 |
|---|---|
| L418 | `double LotForRisk(double stopDistPrice, double &riskUsed)` |
| L453 | `riskUsed = minLotRisk;`（最小手分支） |
| L460 | `riskUsed = lot * perLot;`（正常分支，最终手数 × 每手止损损失） |
| L472 | `riskUsed = lot * perLot;`（降档后最终值） |
| L479 | `if(riskUsed > cap) { g_lotRejCap++; return 0.0; }`（超上限则该笔不开） |
| L889 | `double lot = LotForRisk(stopDistPrice, riskUsed);` |
| L940 | `g_riskMoney  = riskUsed;`（开仓成功后写入） |
| L810 | `DoubleToString(g_riskMoney, 2),`（写进 `trades.csv` 的 `risk_money` 列） |

**额外发现（L945）**：`RiskPctActual = riskUsed / AccountInfoDouble(ACCOUNT_EQUITY) * 100.0` —— EA 会在开仓时打印**该笔风险占净值的百分比**。这给了我们一个直接量测「0.01 手地板 + 最小手超配」真实影响的手段：`InpVerboseLog=true` 时可直接读出每笔的实际风险占比，**不必再靠反推**。

**→ `risk_money` = 该笔在止损位被扫时的实际美元亏损额（含最终手数与最小手超配）。可作 R 分母。我的 R 画像无需重算。**
独立交叉验证：`sl` 出场精确收敛于 **−1.01R**——若分母不是风险额，该比值不可能收敛到 1.00。

## 2. 事实：btc-048 的真实 R 结构（本次从 1071 笔逐笔重算，纠正了我上一条报告的一处误读）

我从 `BT_btc-048/trades.csv` 逐笔计算（`R = pnl / risk_money`）：

| 项 | 真值 |
|---|---|
| 笔数 | 1071 |
| **赢家** | **284 笔（26.5%）**，平均 **+3.204 R** |
| **输家** | **787 笔（73.5%）**，平均 **−0.880 R** |
| 盈亏比（均值比） | **3.642** |
| 总盈 / 总亏 | +28,528.26 / −25,665.22 |
| PF | **1.1116** |
| 期望 R/笔 | **0.2032** |

**按 `exit_reason` 拆开（这是本报告最重要的一组数字）：**

| 出场原因 | 笔数 | 其中赢/亏 | 平均 R |
|---|---:|---|---:|
| `sl` | 600 | 0 赢 / 600 亏 | **−1.02** |
| `trend_exit` | 471 | **284 赢 / 187 亏** | **+1.76**（加权） |
| ├─ 赢的那部分 | 284 | — | **+3.20** |
| └─ **亏的那部分** | **187** | — | **−0.43** |

### 2.1 我纠正了报告_003 的一处错误
报告_003 §1 我把 `trend_exit` 整体写成「R = +1.53」。**真实值是 +1.76**（我把 471 笔的美元均值错配到了 R 上）。同时我上一版把 `trend_exit` 当成「赢家通道」——**错**：471 笔里有 **187 笔是亏的**，且 `trend_exit` 是**唯一**的赢家通道（284 个赢家全部来自 trend_exit，`sl` 从不出赢家）。

### 2.2 PF 的解析式（决定了所有优化方向）
赢家全部走 `trend_exit`、输家有 `sl` 与 `trend_exit` 两类，因此：

```
PF = (w × aw) / (l × al)      w=0.265, l=0.735
   = 1.1116   ←→   aw/al = 3.642
```

**关键结论：PF 只取决于「平均赢 / 平均亏」的比值（3.642），与 R 的绝对大小无关。** 因此任何「把风险放大以抬高美元收益」的做法**不会改变 PF**——它只改变资金曲线斜率与回撤。

由此得到明确目标（平均亏 0.880R 固定）：

| 目标 | 需要平均赢 | 或需要胜率 |
|---|---|---|
| PF 1.20 | 2.93R | 24.8% |
| **PF 1.30** | **3.17R** | **26.3%** |
| PF 1.40 | 3.42R | 27.8% |
| PF 1.50 | 3.66R | 29.2% |

（早期我一版算出「PF 1.11 只需平均赢 2.71R」是公式化简错误，已作废。）

## 3. 推断（标明强度）

**【推断 · 高置信】最有价值的改进目标是那 187 笔亏损的 `trend_exit`（平均 −0.43R）。**
它们是「已经历过浮盈、又被 EMA 反向交叉拖成小亏」的单子。187 × 0.43 = **−80R 的负贡献**，相当于总盈 (+452R) 的 18%。
若能把其中一半转成 0R 或小赢（而不牺牲那 284 个 +3.20R 的赢家），期望值可从 **0.203R → 约 0.24R**（+18%），PF 从 1.11 → 约 1.19。
这正是 `btcswing` 用 **Chandelier 跟踪止盈取代 EMA 交叉**的第一个理由——**不是**「让赢家跑更远」（那要靠 6×ATR 档），而是**先消掉这 187 笔慢性小亏**。

**【推断 · 高置信】btcswing 的窄跟踪档（btc-070, 1.5×ATR）承担「提胜率」任务，宽跟踪档（btc-072, 6.0×ATR）承担「提平均赢」任务。**
两者是**不同的**改进路径，不能互相替代：
- 窄跟踪 → 把 187 笔小亏变成小赢 → 胜率 26.5% → 30%+ → PF 上升（且几乎不牺牲右尾）。
- 宽跟踪 → 让 284 个赢家从 3.20R 走到 4R+ → 平均赢上升 → PF 上升（但可能增加回吐）。
批量4 把两者都放进去，**再加上 btc-082/083 两个组合候选**，就能一次看清哪条路更有效。

**【推断 · 中置信】总调度提醒的「口径陷阱」成立，我接受并修正表述。**
总调度指出：btc-048 的 2.47% 是**起始净值**口径，而它的 net 靠复利（300→3163）放大，跨配置直接比效率不公平。
→ 我接受。**跨配置比较应统一用「起始净值的每笔风险」**。这也意味着我在报告_003 §2 给的「btc-042 效率明显优于 btc-048」**只能作为方向性提示，不能作为定量结论**。
→ 真正的干净做法就是**在单一配置内做线性验证**：btc-065（TrendCore, RiskPct 1.5→0.6）与 **btc-081（btcswing, 同构）**。这两条现在是本线优先级最高的实验。

**【推断 · 中置信】两个新机制（D1 过滤、波动率归一化）必须被当成"待证否"而不是"改进"。**
它们是我加的设计，没有先验证据。btc-073/074 是严格消融，btc-083 是「把两个都删掉的极简版」。**若极简版更优，我会删掉它们**——写进报告而不是默默保留。

**【推断 · 低置信】时段过滤（btc-084）预计影响很小。**
TrendCore 上时段过滤几乎无差异。但我把它标 `low` 优先级，只为完整性，不指望它是答案。
