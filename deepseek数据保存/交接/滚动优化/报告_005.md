## 1. ★★★ 核心发现：我否证了总调度提出的"验证段太小"假设

总调度在 2026-09-12 采纳我的建议，准备跑 **"验证段加长对照"**（`6+3+3` vs `6+6+3` vs `9+3+3`），
依据是我的机制假设：**"验证段只有 3 个月 → 14–28 笔 → 名次本身是噪声"**。

**我用现有数据把这个假设检验了。检验逻辑很直接：**
> **若"验证段样本太小"是主因，那么验证段笔数越多的窗口，预测力（ρ）应当越高。**

### 结果 —— 该假设【零支持】

| 窗口-方向 | **ρ** | 验证段平均笔数 | 测试段平均笔数 | n 候选 |
|---|---:|---:|---:|---:|
| w0-off | +0.246 | **5.2**（最小） | 30.2 | 19 |
| w0-on | +0.007 | 12.0 | 26.3 | 15 |
| w1-on | **+0.599**（最好） | **30.4**（最大） | 18.1 | 26 |
| w2-off | **−0.649**（最差） | 16.3 | **1.4** | 25 |
| w2-on | −0.276 | 14.2 | 15.0 | 64 |

```
Spearman(验证段笔数, ρ) = +0.000   ← ★完全无关
Spearman(测试段笔数, ρ) = +0.700   ← ★强正相关（反方向）
```

**【事实】验证段笔数与预测力**完全无关（ρ=+0.000）**：
- **验证段最小**的 w0-off（5.2 笔）ρ = **+0.246**（尚可）
- **验证段最大**的 w1-on（30.4 笔）ρ = **+0.599**（最好）
- **但**验证段 16.3 笔的 w2-off ρ = **−0.649**（最差）—— 比 5.2 笔的更差

→ **【推断 · 高置信】"把验证段从 3 个月加到 6 个月"极可能不会改善预测力。**

**★ 我因此撤回自己上一轮的建议**（"验证段加长是钉死为什么无效的关键实验"）。
**总调度是采纳了我的建议 —— 所以这个撤回必须先发出，避免浪费机时。**

**效力边界**：n 只有 5 个点，+0.000 也可能只是"样本太小 + 区间不够宽"导致。
→ 但**"没有证据支持"与"有证据支持"的区别是关键的**：现在没有任何数据支持"加长验证段会有用"。

## 2. ★★★ 真正的瓶颈：**测试段（我们用来评判的靶子）本身是噪声**

反方向检验给出 **Spearman(测试段笔数, ρ) = +0.700**，而且最差的窗口有决定性细节：

```
w2-off  ρ = −0.649   ← 最差
        测试段平均只有 1.4 笔
```

**【事实】`w2-off` 的测试段，144 组里平均每组只有 1.4 笔成交。**
→ **用一个"平均 1.4 笔"的净利去评判参数好坏 —— 那个数字本身几乎全是噪声。**
→ **ρ = −0.649 这个"强负相关"很可能根本不是"过拟合到验证段"，而是"靶子本身随机"。**

### 【推断 · 中置信】本线真正的瓶颈是 **OOS 评估靶子的信噪比**，而不是选参方法

| 假设 | 预测 | 数据 | 判定 |
|---|---|---|---|
| H1 验证段太小（总调度的假设 / 我原来的假设） | 验证笔数↑ → ρ↑ | ρ=+0.000 | ❌ **否证** |
| **H2 测试段太薄（靶子噪声）** | 测试笔数↑ → ρ↑ | **ρ=+0.700** | ✅ **有支持** |

**★ 但我必须同时说明 H2 也没有确证 —— 有一个致命细节**：

```
"测试段笔数"是按 144 组的【平均值】算的
```

而**平均值主要反映"策略在那段行情里有多少信号"（regime），不是"评估的精度"**。
→ **所以"测试笔数↑ → ρ↑"也可能是说"行情趋势明确时，所有参数都赚钱，排名自然一致"**，
   —— 那是**行情信噪比**，不是**统计样本量**。
→ **这两个解释（行情清晰 vs 样本充足）我目前分不开。**

### 而且有一个反例必须先摆出来

**即便把 9 个月的测试段串成一条曲线，那也只是 1 个观测。**
我 §1 的 ρ 是**跨参数**的相关；而"方法是否有效"问的是**跨时间**的：
**这个窗口挑出来的参数，下一个窗口还行不行**。后者我只有 5 个点，且 §7.0 显示 3/5 ≈0 或为负。
→ **【事实】把测试段拉长会改善"单个窗口内的秩相关"，但不必然改善"跨窗口的可迁移性"。**

## 3. ★ 口径核证（第二次）：我的数据是 **0 延迟**，不是 60 秒

总调度在 15:2x 又提出：`1 tick = 60 秒`（探针实测 `ticks_per_M1 = 1.000`），
我的 `.set` 无 `InpLatencyTicks` → **"落 base 的 1"** → 实际是 **60 秒延迟口径**。

**这个推理与我 14:55 已核证过的那次是同一个错误**：它假设**该参数存在于我用的编译产物中**。

| # | 证据（可复核） |
|---|---|
| 1 | **含 `InpLatencyTicks` 的源码 mtime = 2026-09-12 14:39:31**（`dsh_BtcSwing.mq5` = 36288 B） |
| 2 | **我的全部网格 ex5 = 2026-09-11 22:44:01**（`opt_wf-*.ex5` = 45076 B）→ **早于 (1) 约 16 小时** |
| 3 | 我 `报告_001` §0.1 记录的当时源码 = **848 行 / 32971 B / mtime 2026-09-11 22:40:14** → 与 (1) 不同版本 |
| 4 | 总调度新跑的 `opt_btcgrid-102.ex5` = **46614 B @ 2026-09-12 14:49:17**；**我的 = 45076 B** → 不同编译产物 |

**→ 【事实】我跑的 ex5 里不存在该 input → 不存在"落 base 的 1" → 我的数据是 0 延迟。**

**★ 我确认总调度关于 tick 尺度的实测是对的**（1 tick = 1 根 M1 = 60 秒；
我在 `analysis\out\eva028_smoke_agent.log` 里也读到测试器日志
"1 minutes OHLC ticks generating" / "126264 ticks, 31566 bars generated" —— **约 4 根 bar 1 个 tick，
与"每 bar 1 tick 量级"一致**）。
**但这个尺度本身暴露了一个设计问题**：
> **1 tick = 60 秒（若在 M15 图上则是 15 分钟）。**
> **而真实网络延迟是 300ms。**
> → **`InpLatencyTicks` 无论设多少（最小 1），都比真实延迟大 200–3000 倍。**
> → **【推断 · 高置信】tick 级"延迟"模拟的是一个量级完全不同的东西（行情推进），不是网络延迟。**
> **用它当"300ms 延迟"的替代品，会把策略的行为改得比真实更糟**（每笔都晚 1 根 bar 成交）。

**→ 建议：与其用 tick 延迟凑一个"看起来有延迟"的口径，
   不如明确把口径写成"次根 K 线成交"（next-bar open），这是一个诚实且可解释的建模选择；
   或者接受"本回测未模拟网络延迟"并在所有结论里标注。**
