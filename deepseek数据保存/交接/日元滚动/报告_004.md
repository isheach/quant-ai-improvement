## 0. 一句话

**`jyrg-008` 与 `jyrg-lat0` 本来就不该相同** —— 前者跑在 **1 tick** 延迟上，后者跑在 **0 tick** 上。

证据不在别处，就在你们自己的 `runexp.py` 里：

```python
runexp.py  L74  BASE_BTCSWING = { ... L88:  "InpLatencyMs": "0", "InpLatencyTicks": "1", }
           L96  BASE_JPYREV   = { ... L109: "InpLatencyMs": "0", "InpLatencyTicks": "1", }
           L111 BASE_MEANREV  = { ... L122: "InpLatencyMs": "0", "InpLatencyTicks": "1", }
           L175 BASE_PARAMS   = { ... L206: "InpLatencyMs": "0", "InpLatencyTicks": "1", }

batch_run.py  L158  merged = dict(base)
              L159  merged.update({k: str(v) for k, v in params.items()})   ← params 覆盖 base
```

**→ 我第一批的 `jyrg-008`，`params` 里【没有】`InpLatencyTicks`（那时 `dsh_JPYRev` 还没有这个参数）→ 它落到了 base 的 `"1"`。**
**→ 我第二批的 `jyrg-lat0` 显式写了 `"0"` → 它覆盖成了 0。**

**→ 两个不同的参数值、两个不同的结果 —— 完全正常。测试器没有不确定。**

### 1.1 为什么这个假警报很危险（我必须明说）

总调度据此推出的那句话是：
> 「**若测试器有随机性，那'逐位相同'是【强证据】，而'逐位不同'就【不能作为差异的证据】。**」

**→ 如果按这个结论走，会连带作废或降级一批本来是**正确**的判定**，例如：
- 滚动优化线「`InpLatencyMs` 是空操作」（144/144 逐位相同）
- 比特币线「`btc-204 ≡ btc-195 ≡ btc-211`」
- 网格通道与单跑通道等价

**→ 【推断 · 高置信】MT5 的 Model=2 测试器在「同 ex5 + 同输入 + 同 tick 数据」下是确定的**（该模型没有随机源）。
**→ 更省事的解释永远是"有隐藏的输入差异" —— 这次就是。**
**→ 建议写进项目纪律：**「两个 run 结果不同时，**先穷举所有 input（含 BASE 合并进来的）逐项比对**，再考虑环境/随机性。」

**★并且这条已经查实了**：`BASE_*` 会往每个 run 里注入 4 个 run 自己没写的键
（`InpLatencyMs`、`InpLatencyTicks`、`InpWriteAudit`、`InpVerboseLog` …）。
**我请求的 `params` 里没写 `InpLatencyTicks`，就等于把控制权交给了 base 的默认值。**

## 3. ★★ 延迟 A/B 本身：结论有效，而且这是全项目第一次真正测到延迟

**三臂（lat0/lat3/lat30）都【显式】设了 `InpLatencyTicks`，所以这个 A/B 是干净的控制实验。** 结果有效：

| | 0 tick | 3 ticks | 30 ticks | 变化 |
|---|---:|---:|---:|---|
| net | −9.84 | −15.66 | −16.00 | **多亏 $6.16** |
| DD% | 7.10 | 9.44 | 10.47 | **+47%（相对）** |
| 笔数 | 224 | 224 | **222** | 基本不掉 |

**★关键判据（我在 `报告_001` §2.5 就预写过）**：**笔数基本不掉 → 延迟是"成交价变差"，不是"挂单被拒"。这是健康形态。**
**→ 【事实】`InpLatencyTicks` 在 MT5 测试器里【真实生效】—— 全项目第一次有数据支持这句话。**

### 3.1 边际成本不光滑，我要如实标注

```
0→1 tick : Δnet = −3.73
1→3 ticks: Δnet = −2.09
3→30 ticks: Δnet = −0.34      ← 边际骤降
```

**→ 【推断 · 中置信】这是【饱和】形态，不是线性。** 若 Model=2 里 tick 之间跨的模拟时间较长（见 §4），
那么 3→30 tick 可能已经从"晚一点成交"变成"整根 bar 都过去了"，信号本身已过期，再多等也差不多。
**→ 但必须标注：这是单条路径、只有 224 笔、且三个数字都靠近 0（−9.84 ~ −16.00），所以逐点成本估计是有噪声的。**
**→ 我能说的稳健结论只有两条：①延迟真实生效 ②延迟单调变差。逐点幅度不作强结论。**

## 4. ★★★ 一个更大的问题：**1 个 tick 到底等于多少模拟时间？300ms 在 Model=2 里可能根本无法表示**

**全项目的延迟口径都建在 `InpLatencyTicks` 这个【计数器】上，但没有人知道它对应多少时间。**

**常见说法**：MT5 的 `Model=2`（1 minute OHLC）**每根 M1 生成约 4 个 tick（O/H/L/C）**
→ **1 tick ≈ 15 秒**（【推断 · 中置信，未验证】）

**若这个说法成立，那么全项目的延迟表述都要重写：**

| 声明 | 实际 |
|---|---|
| `InpLatencyMs=300`（硬约束要求的口径标记） | **在测试器里是空操作**（`Sleep` 不推进模拟时间；新版 `dsh_JPYRev` 已整段删除） |
| `InpLatencyTicks=1`（★四个 BASE 字典的默认值） | **≈ 15 秒 = 目标 300ms 的 50 倍** |
| 想要精确 300ms | **≈ 0.02 个 tick —— 在 Model=2 里【无法表示】** |

**→ 【推断 · 中置信】结论：在 Model=2 下，「模拟 300ms 延迟」这件事**做不到**。
能做的最小延迟是 `InpLatencyTicks=1`，而它比目标大两个数量级。
→ 于是全项目其实只有两种口径：**「0 延迟」和「≥1 tick（≈15 秒）」，中间没有 300ms 这个点。**

**★我不把这条当定论** —— 我交付一个**只测量、不交易**的探针 EA（见 §5），跑 1 个月就能把它变成事实。

**★这条对网格判定的意义**：我网格的 `InpLatencyTicks=0` ⇒ 网格结果全是 **0 延迟**。
真实世界介于"0 延迟"和"1 tick≈15s"之间（真实 300ms 远小于一个 tick），**所以网格的真实表现会比 0 延迟差、但比我上面那张表的 1 tick 好。**
**→ 无论如何都【不会变得更好】 ⇒ `报告_003` 的网格否证方向不变。**
