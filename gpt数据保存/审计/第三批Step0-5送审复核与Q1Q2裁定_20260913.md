## 三、第 1 节复核：两条更正成立

### 3.1 JPY 缺行

## 四、第 3.2 节复核：反向审计偏差成立，但修复还需两道工程闸

R4 首版的事实链是闭合的：HTML 403 笔、审计 399 行，漏掉的四笔金额合计 `-17.65 USD`，正好解释审计 `-30.84` 与报告 `-48.49` 的差额。漏掉的四笔全是止损，故这是系统性乐观偏差而非随机缺失。

已完成的修复方向正确：

- `DealSeen()` 不再在函数入口提前登记；
- `InpCloseAtEnd` 在窗口末主动平仓，使通常平仓路径也能写入审计；
- R4 记录了 `position_id`、开平时间、OCP 和成本拆分。

仍需登记的两个工程风险（不推翻本次 R4 结果，但必须在 MR30 前修）：

1. `dsh_JPYRev_R4.mq5` 的 `FileWrite()` 返回值没有被检查；当前代码在调用后直接递增 `g_writtenDeals`。如果写盘失败，ticket 仍可能已进入去重表而永久漏记。
2. `DealSeen()` 使用固定 4096 槽数组；数组满后函数返回“未见过”而不再保存新 ticket，可能导致重复写入。达到上限应立即把 `audit_failed` 置位并停止，或改用可扩容集合。

此外，R4 CSV 表头出现两次 `entry_time`（原始列索引 9 和 20）。六个现有 run 两列值完全相同，所以本次数字不受影响；但 MR30 必须使用唯一列名，避免 `csv.DictReader` 静默覆盖字段。

## 五、第 3.4 节更正：正确判据下为 6/6

原执行器的错误在 `step3_run_r4.py`：

```python
html_deals == len(rows) * 2
```

这只适用于每个 closing row 恰好对应一个 opening row 的完整开平场景，不能用于部分平仓。MT5 的 `Total Deals` 应从 Deals 表的 `Direction` 列重建：

```text
closing_rows = count(Direction == "out")
opening_rows = count(Direction == "in")
Total Deals == opening_rows + closing_rows
closing_rows == audit closing rows
Total Trades == closing_rows
```

独立 v2 结果如下：

| 场景 | HTML in | HTML out | HTML Total Deals | HTML Total Trades | 审计 closing rows | 净利差 | OCP | 独立公式 | 结论 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| LONG_A / LONG_B | 403 | 403 | 806 | 403 | 403 | 0.00 | 403/403 | 403/403 | 通过 |
| SHORT_A / SHORT_B | 399 | 399 | 798 | 399 | 399 | 0.00 | 399/399 | 399/399 | 通过 |
| PARTIAL_A / PARTIAL_B | 790 | 791 | 1581 | 791 | 791 | 0.00 | 791/791 | 791/791 | 通过 |

同时核对到：六个 CSV 的 `deal_ticket` 均唯一；`profit + swap + commission = net` 全部成立；`audit_failed=0` 且 `written_deals=审计行数`；A/B 成对输出逐行一致。

原报告的“5 项通过、1 项未过”应保留为历史送审状态，不应继续作为当前 R4 结论。建议新增更正附件，不改写原报告。
