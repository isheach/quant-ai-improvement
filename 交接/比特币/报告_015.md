## 1. ★回答总调度的问题：`btc-138` 的 `InpUseVolNormalize` 是 **false**

总调度问："`btc-138` 的 `InpUseVolNormalize` 到底是 true 还是 false？这决定了哪套基值才是 btc-138 的真实口径。"

**答案（证据）**：我查了 outbox 里 `btc-134/137/138/139` 的 `params` 字段 ——
```
btc-138: InpUseVolNormalize = 【未出现在 params 里】
```
`params` 只记录**我在请求里显式写的项**。`btc-138` 的请求里**没有**这一项 → **它取单跑通道 BASE 的值**。

而单跑通道的 BASE 是 `BASE_BTCSWING`，我读 `btcswing.set` 得到：
```
InpUseVolNormalize=false
```
→ **结论：`btc-138` 的 `InpUseVolNormalize = false`（来自基线），不是源码默认的 true。**

**★所以我此前（报告_014 §4.2）那句"btc-138 的 +412.52 是在源码默认 `UseVolNormalize=true` 下取得的"是错的，我撤回。**
→ **这同时证明：单跑通道的 BASE 是【被有效传递】的** —— 总调度担心的"另一个 bug（单跑通道 BASE 未传递）"**不存在**。✅

**★由此我得承认一处**：我用"网格修复前的 `opt_btcgrid-101.set` 里 `InpUseVolNormalize` 落回源码默认"这一**事实**，去推断"btc-138 也是源码默认" —— **这是把网格通道的行为错误地外推到单跑通道**。两个通道的基底本来就不同（这正是报告_014 §3 的结论本身），我却在同一份报告里犯了跨通道外推。**这是我的逻辑错误，不是总调度的。**

## 6. 下一步（报告_013 §7 的分支已触发）：**regime 切换**

### 6.1 机制设计（针对已量清的失效原因）
**两个极限的失效根因不同**，所以要同时解决：
- 只做多的失效：**BTC 跌破 D1 EMA200 后长期不回头 → 只做多被全面禁止 → 43 个月空转**；
- 双向的失效：**在下跌趋势里"也做空"**，与不良信号混在一起 → PF 被摊薄到 1.12。

**→ 方案：把"停牌"换成"**仅做空**"，而不是"也做空"**：
```
regime = 价格 > D1 EMA  ?  +1  :  -1        （沿用已验证的水平判据）
若 regime = +1 → 只允许做多（禁止做空）
若 regime = -1 → 只允许做空（禁止做多）
```
**与双向的关键区别**：双向是"两个方向都允许、由信号决定"；本方案是"**regime 决定唯一允许的方向**"。
→ 理论上：**牛市只多 → 保住高 PF；熊市只空 → 补上 43 个月的覆盖率**。**两个极限的失败原因被分别消除。**

### 6.2 实现（EA 改动，我会先自检再交编译）
新增一个 input：
```
input bool InpRegimeSwitch = false;   // ★true=按 D1 水平判据切换唯一允许方向（牛市只多/熊市只空）
```
逻辑（`EvalSignal()` 内，已有 `trendUp` 可用，改动最小）：
```
if(InpRegimeSwitch) {
   if(trendUp > 0) InpAllowShort 局部禁用;   // 只多
   else            InpAllowLong  局部禁用;   // 只空
}
```
**注意**：要**局部**禁用（不修改 input 本身），否则会污染其它逻辑。

### 6.3 我会先做的自检
- 括号/方括号/圆括号 net=0、块注释闭合（沿用字符级扫描器）
- 新 input 全部被引用
- 不改动任何现有默认行为（默认 `false`）
