### 2.1 ★我的更正 E7：所有网格 run 的 `.set` 里 `InpLatencyMs` 其实是 **0**

**我在 `报告_001` / `报告_002` / `报告_003` 里都写着"`fixed` 里写 `InpLatencyMs=300`（口径标记）"。**
**→ 【事实】L245 在我 `fixed` 之后执行，把 300 无条件改写成 0。所以那些 `.set` 里是 0。**

**这不影响任何数值结论**（`InpLatencyMs` 在测试器里是已证实的空操作），
**但它意味着我报告里的"300 口径标记"这句话，对网格 run 是【不成立的】**。
**→ 我更正：本线全部网格 run 的真实口径是 `InpLatencyMs=0` + `InpLatencyTicks=0`（完全 0 延迟）。**

**★顺带说明：`batch_run.py` 的单跑通道【没有】这类改写**（我 grep 过，`batch_run.py` 里没有任何 `InpLatency` 行），
所以那 8 条逐条 + 7 条控制组的 `InpLatencyMs=300` 是**照我写的执行**的。

### 2.2 定案：我第一批 6 个 W0 网格带 1 tick 的**确切机制**是 L246–248

**不再需要"从 `BASE_JPYREV` 推断"** —— 网格通道自己就有一条 `if 没写 then 1` 的规则。
**→ 我第一批的 `jpygrid_fixed()` / `jpyrev_fixed()` 都没写 `InpLatencyTicks` → 落到 "1"** ✅
**→ 我第二批以后的所有网格请求都**显式**写了 `"InpLatencyTicks": "0"` → `if` 为假 → 保持 0** ✅
（`报告_004` §2.2 的结论成立，且现在有了行级证据。）

### 2.3 我的网格 EA 没有 BASE 注入（L228 `"jpygrid": {}`）

**→ 我的网格请求的参数集是"干净"的：只有我写的 + EA 源码默认值，没有第三方注入。**
**→ 这解释了为什么 `jyrg-c0r` 能精确复现 `c0-base`（网格 EA 的输入完全由我控制）。**

## 3. 黄金线口径：混合（总调度 grep 结果，我采信并纳入）

```
gold run_*.ini 共 122 个：带 InpLatencyTicks 的 26 个（值=1），不带 96 个
```

**→ 【事实】黄金线的 585 次回测【横跨两种延迟口径】。**
**→ 我对这条的读法与总调度一致**：它的"含真实 tick 延迟"声明**对网格批不成立、对后期逐条成立**。
**→ 而且这提示黄金线后期"结果与之前不同"的现象里，可能叠加了**延迟口径变化**这个此前未识别的因子。**
**★我建议黄金线做一次最小检查**：把 `gold-096…121` 中任意一条，用 `InpLatencyTicks=0` 重跑一次；
若结果与 1 tick 版本不同，则它那批结论的口径需要分段标注。

**★总调度用 grep `.ini` 而不是用 ex5 大小来判定口径 —— 这是更权威的做法，我确认采纳。**
（理由：`.ini` 是每个 run **实际**喂给 MT5 的输入记录；ex5 大小只能反映二进制版本，反映不了参数。）
